## 1. 先厘清：RISC-V 语境下"scratch"是三个不同的东西

| 说法 | 指什么 | 是否有 ISA 级约定 |
| --- | --- | --- |
| `t0`–`t6` | ABI 的 caller-saved temporaries | 否，纯 psABI |
| `mscratch` / `sscratch` | 特权态 CSR，存 hart-local 上下文指针 | 是，但和用户态代码无关 |
| "远跳缺的那个寄存器" | **本项目的 scratch** | 否，ISA 完全不提，是工具链自己约定的 |

本项目 `SCRATCH.md` 讲的是第三种。前两种的存在恰好说明设计者对这个词的态度：
**寄存器用途一律放在 ABI / 特权层解决，不往用户态 ISA 里塞。**

## 2. 为什么会有"远跳缺 scratch"这件事：编码预算的直接后果

Waterman 论文 §3.1（p.23–25）把范围写死了：

- 条件分支 B-type：`imm[12:1]`，±4 KiB。
- `jal` J-type：`imm[20:1]`，±1 MiB。
- `jalr`：`rs1 + 12-bit`，±2 KiB，**间接**。

于是"跳出 ±1 MiB"这件事在 RISC-V 上只能表达成"先算出地址，再 `jalr`"，
即 `auipc` + `jalr` 两条。这不是没想到长跳，而是故意的取舍：
把立即数字段压小，换取固定 32 位编码、寄存器号够宽、扩展空间够大。

同一节里对 delay slot / condition code 的处理，也是同一种取舍口味：

> "for deeper pipelines and for machines with superscalar instruction dispatch,
> delay slots increase complexity and offer vanishing benefit."

> "In RISC-V, we reasoned that we could achieve better code size and dynamic
> instruction count by folding the comparisons into the branch instruction."

**这条对 `SCRATCH.md` 很关键**：compare 折进 branch，才使 RISC-V 不需要 MIPS 那种
`$at`（MIPS 的 `blt a,b,L` 要展开成 `slt $at,a,b; bne $at,$0,L`）。

## 3. 设计者的答案不是"预留一个 scratch"，而是"让 rd / link 自己当 base"

这是本次查证最重要的发现，也是 `SCRATCH.md` §1 那句
"`(jump-far link s L)` 且 link 非零时不需要 scratch" 的上游出处。

### 3.1 psABI 的 `call`

`riscv-elf.adoc`，"Procedure Calls" 一节，`call symbol` 展开为：

```asm
    auipc ra, 0           # R_RISCV_CALL (symbol), R_RISCV_RELAX
    jalr  ra, ra, 0
```

`auipc` 的**落点就是 link 寄存器自己**，`jalr` 再拿它当 base。
所以远调用永远不需要"额外的" scratch——`ra` 本来就是这次调用的 trash。

> `R_RISCV_CALL` / `R_RISCV_CALL_PLT` ... "are associated with pairs of
> instructions (`AUIPC+JALR`) generated by the `CALL` or `TAIL`
> pseudoinstructions."

### 3.2 GNU as 的伪指令表把这件事写成了编码

`opcodes/riscv-opc.c`：

```c
{"call", 0, INSN_CLASS_I,     "c",   (X_RA << OP_SH_RS1)|(X_RA << OP_SH_RD), M_CALL, ...},
{"call", 0, INSN_CLASS_I,     "d,c", (X_T1 << OP_SH_RS1),                     M_CALL, ...},
{"tail", 0, INSN_CLASS_I,     "c",   (X_T1 << OP_SH_RS1),                     M_CALL, ...},
{"tail", 0, INSN_CLASS_ZICFILP,"c",  (X_T2 << OP_SH_RS1),                     M_CALL, ...},
{"tail", 0, INSN_CLASS_I,     "c,s", 0,                     M_CALL, match_rs1_nonzero, ...},
{"jump", 0, INSN_CLASS_I,     "c,s", 0,                     M_CALL, match_rs1_nonzero, ...},
```

逐条读（`riscv_call(destreg, tempreg, ...)` 生成 `auipc tempreg, hi; jalr destreg, tempreg, lo`）：

| 写法 | `destreg` | `tempreg`（= auipc 落点 = base） | 需要额外 scratch？ |
| --- | --- | --- | --- |
| `call sym` | `ra` | `ra` | **否** |
| `call rd, sym` | `rd` | `t1` | 是，**汇编器直接写死 t1** |
| `tail sym` | `x0` | `t1` | 是，**汇编器直接写死 t1** |
| `tail sym, rs` | `x0` | `rs` | 由用户显式给 |
| `jump sym, rs` | `x0` | `rs` | 由用户显式给 |

这正是本项目的三种情况：
- `jump-far link L`（link ≠ 0）→ 对应 `call sym`，**不用 scratch**；
- `jump-far x0 L` → 对应 `tail sym`，**缺 scratch**，上游的做法是**固定用 t1**；
- 想指定 → 上游提供了 `tail sym, rs` / `jump sym, rs` 这种显式形式（= `SCRATCH.md` 方案 A 的接口）。

### 3.3 `la` 同理

`tc-riscv.c`：

```c
pcrel_load (rd, rd, imm_expr, "addi", BFD_RELOC_RISCV_PCREL_HI20, ...);   /* M_LA */
```

`la rd, sym` = `auipc rd` + `addi rd, rd`，**临时寄存器与目的地是同一个**。
所以"远 la 需要 scratch"只在 `la` 的形状里同时要 base 和结果时才成立
（例如 `la-frame` 有两处用途），这一点 `SCRATCH.md` 的 `riscv-help/la.rkt`
判断是对的，但它不是 autoconf 那种"汇编器自己找寄存器"。

### 3.4 结论：RISC-V 没有 `$at`

MIPS 需要 `$at` 的两个理由，RISC-V 都用别的方式消掉了：

1. 伪 compare-and-branch → 把比较折进 branch（§2 引用）；
2. 远跳的 base → 用 link / rd 自己当 base（§3.1–3.3）。

所以 RISC-V 的 ISA 和 ABI 里**没有任何"保留给工具链"的用户态寄存器**。
需要额外寄存器的地方，全被推到两处：
- 汇编器伪指令的**固定约定**（`tail` → `t1`），
- 编译器的**寄存器分配 / 活跃分析**（见 §4）。

这也解释了为什么 `SCRATCH.md` 找不到"RISC-V 规定用哪个 scratch"的答案——
**它确实没有规定**。

## 4. 现实工具链怎么解决"块边缘没有空寄存器"

### 4.1 汇编器 / 伪指令层：固定 t1（方案 E 已被生态采纳）

见 §3.2。补充两点：

- GAS 在被 `Zicfilp`（cf-protection-branch）启用时改用 **`t2`/x7**：
  `{"tail", ..., INSN_CLASS_ZICFILP, "c", (X_T2 << OP_SH_RS1), ...}`。
  也就是说"固定 scratch"这个约定本身也会被别的扩展挤掉,
  所以它必须是**可配置/可覆盖**的，而不是硬编码进 IR 语义。
- 为什么固定用 t1 是合法的？因为在 `tail` / `call` 这种**控制转移边界**上，
  caller-saved 的临时寄存器按 ABI 已经死了。
  ⚠️ 但 `SCRATCH.md` 的 `jump-far x0 L`（函数内远尾跳）**没有这个保证**——
  ABI 只在跨函数调用时送你 scratch。这一点上游没有解决，本项目的谨慎是对的。

### 4.2 LLVM 代码生成层：branch relaxation 用 RegScavenger + 溢出兜底

`llvm/lib/Target/RISCV/RISCVInstrInfo.cpp`，`RISCVInstrInfo::insertIndirectBranch`：
这是 BranchRelaxation 发现"跳太远"时真的去生成 `auipc`+`jalr` 的地方。
它做的事情，几乎逐条对应 `SCRATCH.md` §6 的清单：

1. 造一个虚拟寄存器 scratch，插入 `PseudoJump`（= `auipc scratch; jalr x0, scratch`）；
2. `RS->enterBasicBlockEnd(MBB)` + `RS->scavengeRegisterBackwards(..., RestoreAfter=false, AllowSpill=false)`
   ——**反向、按块尾的活跃性找一个死寄存器**。这正是 `SCRATCH.md` §4.2 说的
   "edge-sensitive / 块尾 liveness"，LLVM 用的是 RegScavenger 的近似版本；
3. 找不到时**不报错**，退化成：挑 `s11`（RVE 用 `s1`），
   用 `RVFI->getBranchRelaxationScratchFrameIndex()` 里的**栈槽**保存，
   跳到 `RestoreBB`，在 `RestoreBB` 里 reload 再跳到 `DestBB`；
4. 栈槽都没有（prologue 没预留）才
   `report_fatal_error("underestimated function size")`。

对 `SCRATCH.md` 的两处修正/补强：

- §4.5 "不能在跳走之后 restore" —— 结论对（确实不能在 `jalr` 之后 restore），
  但上游的解法是**跳到另一个块再 restore**（`RestoreBB`），
  即 `SCRATCH.md` §4.5 自己提到的 trampoline / 保存恢复协议。
  所以"不可能"应该改写成"不可能在**尺寸不变、不插块**的前提下做到"。
- §6.7 "仍然会失败" —— 上游确认了：失败时**报错也是一种合法终局**
  （`underestimated function size`），而不是必须给答案。

### 4.3 远尾跳：LLVM 直接写死 x6

`llvm/lib/Target/RISCV/RISCVInstrInfo.td`：

```tablegen
// PseudoTAIL is a pseudo instruction similar to PseudoCALL and will eventually
// expand to auipc and jalr while encoding.
// ... PseudoTAILX7 is the software-guarded variant that uses X7 (t2) as the temp
// register for AUIPC+JALR expansion ...
// Annoyingly we have to clobber X6 and X7 because the assembler may use Zicfilp
// to decide which register to use.
let isCodeGenOnly = 0, Defs = [X6, X7] in
def PseudoTAIL : Pseudo<(outs), (ins call_symbol:$dst), [], "tail", "$dst">, ...
```

注意 `Defs = [X6, X7]`：编译器在**指令选择阶段**就承认这个伪指令会写坏 t1/t2，
让寄存器分配器自己避开。这和 §3.2 GAS 的固定 `t1` 是同一个约定，
只是 LLVM 把它上升成了"声明的副作用"——这正是 `SCRATCH.md` 方案 E 的正确工程形态：
**不是"偷偷用一个寄存器"，而是"在 IR 里声明 clobber，让上层绕开"。**

## 5. 为什么 linker 不给答案：relaxation 只能减不能增

`riscv-elf.adoc`，"Linker Relaxation"：

> "As this transformation may delete bytes (and thus invalidate references that
> are commonly resolved at compile-time, such as intra-function jumps), code
> generators must in general ensure that relocations are always emitted when
> relaxation is enabled."

配合 `R_RISCV_ALIGN`（"needed because linker relaxation can shrink ..."）可以确认：
RISC-V 的 linker relaxation 模型是**单调收缩**的，没有 veneer、没有"变长"通路。

所以 `SCRATCH.md` §5.3 / §7 方案 F 的判断成立且有据：
**RISC-V 生态把"远"这件事整体推给了代码模型**
（`medlow`/`medany`、函数别超 ±1 MiB、局部转移别超 ±4 KiB），
而不是让链接器在最后关头找寄存器。
`-mcmodel` 的存在本身就是这个设计哲学的产物。

## 6. 另一个方向的证据：设计者明确拒绝"给 OS 预留用户寄存器"

`src/priv/machine.adoc`，`mscratch` 的 NOTE（原文）：

> "The MIPS ISA allocated two user registers (`k0`/`k1`) for use by the
> operating system. Although the MIPS scheme provides a fast and simple
> implementation, it also reduces available user registers, and does not scale
> to further privilege levels, or nested traps. It can also require both
> registers are cleared before returning to user level to avoid a potential
> security hole ...
>
> The RISC-V user ISA was designed to support many possible privileged system
> environments and so we did not want to infect the user-level ISA with any
> OS-dependent features. The RISC-V CSR swap instructions can quickly
> save/restore values to the `mscratch` register."

`src/priv/supervisor.adoc`，`sscratch`：

> "At the beginning of a trap handler, software normally uses a CSRRW
> instruction to swap `sscratch` with an integer register to obtain an initial
> working register."

这两段是**唯一**能看到设计者正面谈"scratch 寄存器该怎么提供"的地方，
而结论非常明确：

- **不要在用户态 ISA 里为某个软件层预留寄存器**；
- 用**一条交换指令 + 一个 CSR** 把"临时借用"变成显式的、可嵌套的操作。

推论到本项目：`SCRATCH.md` 方案 A（前端预留池 + 后端填洞）在方向上和这个哲学一致
——预留是 ABI/调用约定层的事，不是 ISA 层的事；而方案 E（全局固定 t6）要小心，
它相当于把一个"平台约定"硬编码进后端，正是 `mscratch` 那段 NOTE 反对的形态。
**折中做法：默认池 = `t1`（与 GAS/LLVM 一致），但池的内容必须是输入参数。**

## 7. 还有一条：连 `gp` 都不是 ISA 固定的

`riscv-elf.adoc`，`Tag_RISCV_x3_reg_usage`：

> "`x3`/`gp` could be used for global pointer relaxation, as a reserved platform
> register, or as a temporary register."

`0` = 固定但用途未知，`1` = gp relaxation，`2` = shadow stack pointer，`3` = **临时寄存器**。

也就是说：RISC-V 连"哪个寄存器被平台占掉"都做成了**对象文件里可协商的 tag**，
合并冲突时报错。这是本项目 `riscv-help/scratch.rkt` 那几条
"非零 / 不重复 / 不与 rd、base、link 冲突"检查在生态里的对应物：
**不是猜，是声明 + 校验。**

## 8. 逐条核对 `SCRATCH.md`

| `SCRATCH.md` 的判断 | 上游证据 | 结论 |
| --- | --- | --- |
| §1 `jump-far` 的 link 非零时不需要 scratch | psABI `call` = `auipc ra; jalr ra,ra`；GAS `{"call","c", X_RA\|X_RA}` | ✅ 完全正确，是 psABI 明文 |
| §1 远 `la` 需要 scratch（当 base≠rd） | GAS `pcrel_load(rd, rd, ...)` | ✅ 正确，但常见形状里 rd 自己就是 base |
| §2 扫 CFG 块结构不能判断"空 reg" | LLVM 用 RegScavenger 而非块扫描 | ✅ 正确 |
| §4.2 需要 edge-sensitive liveness | LLVM `scavengeRegisterBackwards` + `enterBasicBlockEnd` | ✅ 方向正确（LLVM 用的是块尾近似） |
| §4.5 不能在跳走之后 restore | LLVM 用 `RestoreBB` 跳到别处再 reload | ⚠️ 需限定"在不插块、不改尺寸的前提下" |
| §4.6 插变长指令破坏 relax 契约 | psABI：relaxation 只删字节 | ✅ 正确，有明文 |
| §5.3 消掉远形式优于猜寄存器 | psABI / `-mcmodel` / 无 veneer | ✅ 正确 |
| §6.7 找不到就报错 | LLVM `report_fatal_error("underestimated function size")` | ✅ 上游确认这是合法终局 |
| §7 方案 A（预留池 + 填洞）推荐 | GAS `tail sym, rs` / `jump sym, rs` 的显式接口 | ✅ 生态里已有同形状接口 |
| §7 方案 E（全局固定 t6） | GAS `tail` → x6，LLVM `PseudoTAIL Defs=[X6,X7]` | ✅ 生态默认做法，但必须可覆盖、且要在 IR 里声明 clobber |
| §7 方案 D（后端自动 liveness） | LLVM `insertIndirectBranch` | ✅ 但上游只用在 branch relaxation，且有溢出兜底 |
| §7 方案 F（交给 linker） | relaxation 只减不增、无 veneer | ✅ 当前 RISC-V 上走不通，判断正确 |

## 9. 对实现的建议（按上游对齐）

1. **默认池用 `t1`，不要用 `t6`。**
   GAS 和 LLVM 都已经把 t1/x6 当成"远尾跳的约定 scratch"。
   和生态一致，前端就少一条自定义 ABI 约定；t6 留给普通分配。
2. **池是参数，不是常量。**
   `Zicfilp` 一类的扩展会让"固定 scratch"漂移（GAS 从 t1 改成 t2），
   `Tag_RISCV_x3_reg_usage` 也说明连 `gp` 都能被重新指派。
   所以 `scratch-fill` 的池必须来自输入（前端 / 选项），后端只负责校验。
3. **`scratch-fill` 要有"声明 clobber"的出口。**
   LLVM 的做法值得抄：不是后端偷用一个寄存器，而是让 IR 层知道
   "这个 form 会写坏池里的寄存器"，从而在寄存器分配时避开。
   对当前流水线，最小版本是：`layout` 阶段的 `scratch-hole?` 已经能提前报出"这里要 scratch"，
   把它做成对前端的**需求信号**（`SCRATCH.md` 方案 C 的两遍编译）比事后填更干净。
4. **自动选择（方案 D）如果要做，照抄 LLVM 的三段式：**
   反向 scavenge → 失败则 spill 到 prologue 预留的栈槽 + `RestoreBB` → 再失败才报错。
   注意这条路会**改尺寸、加块**，只能放在 `relax` 之前，
   与 `CONSTRAINTS.md` 的分段模型兼容。
5. **函数内 `jump-far x0 L` 是唯一没有豁免的地方。**
   上游（GAS/LLVM）都没解决它，只是假设它不发生（代码模型）。
   本项目要么在代码模型上保证它不发生，要么就老老实实保留池 —— 这个判断可以保留。

## 10. 一句话总结

> RISC-V 设计者**从没打算在 ISA 里给长跳准备 scratch 寄存器**：
> 他们先靠"比较折进 branch"和"rd/link 自己当 base"把需求压到最小，
> 剩下的那一点点（link=x0 的远尾跳）交给汇编器/编译器的**固定约定（t1）**
> 加**ABI 的 caller-saved 豁免**解决，而不是造一个 `$at`。
> 凡是"要长期占有"的寄存器用途，他们一律做成可协商的（psABI tag、CSR swap），
> 不做成 ISA 语义。
